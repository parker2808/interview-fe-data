## 1. Main readability problems

Problem IDs below are referenced in the checklist. K = knowledge base, Q = Q&A, X = both.

### K1. No plain-language explanation; topics open on an expert scenario
Every topic starts with a "What they actually ask" scenario and goes straight to internals. The concept itself is never defined.
> `vue3` 5.1.1 Virtual DOM opens: "A 100k-row Vue 3 table hitches on filter. You say “diff the trees and patch the DOM.” They push: *what does the compiler change about that story?* They want **patch flags, static hoisting, and the block tree**…"

It never says what a virtual DOM is, why it exists, or what "patch" means.

### K2. Undefined jargon and acronyms (also applies to Q&A)
Acronyms and internal names show up without being defined: INP, TBT, LCP, CLS, TDZ, RSC, BFF, ISR, SWR, patch flags, block tree, `flushSync`, `scheduler.yield()`, microtask starvation.
> "**How to verify.** Performance panel — long tasks >50ms, INP, total blocking time — not the puzzle output."

### K3. Telegraphic, over-packed bullets
The 4-item `Decision. / Why. / Trade-off. / How to verify.` list packs 3–5 separate ideas into each bullet, in note-taking fragments.
> "**Trade-off.** `v-if` / `v-for` at a block root, `v-bind="obj"`, and `v-html` force coarser flags (`FULL_PROPS`, unkeyed fragments). Render functions / JSX lose compiler hints. A wrong memo condition paints stale UI. A new object/array literal as a prop every render (`:style="{}"`) makes the child look dynamic even when values are equal."

### K4. Rigid, redundant template; "key takeaways" are tangents
The `Takeaway` box just restates the first sentence of `Interview phrasing`, and `key-takeaways` brings in new tangents instead of summarising the topic.
> Takeaway: "The call stack empties, then every microtask runs before the browser can paint…" / Interview phrasing: "After the call stack empties, every microtask runs before the browser can paint."
> Key takeaway on the *event loop* topic: "React 18 `flushSync` is the same hammer; using it in a list wrecks INP."

### K5. Orphan follow-up list
Each topic ends with an unlabeled `list` of 4–5 questions. It has no heading and no answers, so the reader can't tell what it is or learn from it.
> "- What is microtask starvation, and how would it show up in a Performance trace?"

### K6. Thin or missing examples
About 70 topics have no code at all, including core ones like `vue3` 5.1.1 Virtual DOM, 5.1.8 `nextTick`, 5.1.11 Lifecycle, 5.2.1 Teleport, and `nuxt` 6.5 `useAsyncData` vs `useFetch`. Where code exists, it rarely shows the output or walks through what happens line by line.

### K7 / Q6. Vietnamese is code-switched or literal machine translation
The vi text keeps English grammar words and idioms, leaves labels and generic headings in English, and sometimes reads as nonsense.
> js 1.1.3 vi: "Câu thật: bạn set ref, đọc ngay `el.offsetHeight`, nhận giá trị cũ; hoặc page freeze khi `await` trong vòng parse chặt."
> leadership 17.4 vi: "Để lựa chọn đảo được đi (đặt tên CSS)" (a literal rendering of "let reversible choices go").
> Q&A vi: "**Failure mode:** Đói microtask…", "**Measure:** Panel Performance…", "**Production gotchas:**" (labels left in English in 50 answers).

Generic headings are also left untranslated, e.g. "1.1. Core Concepts", "9.1. Core Performance".

### K8. Fragmented structure in 3 docs
`build-tools` 12.1, `networking` 13.1 and `system-design` 16.1/16.2 are split into H4 micro-sections of 1–2 blocks each ("HMR :: one list", "Draw boxes :: one code block"). The topic's own boxes are scattered around them.

### K9. Missing content: `web-apis` is a stub (regression)
The seed commit `34e8ac5` had 6 full topics: 4.1 IndexedDB, 4.2 Web Workers, 4.3 Service Workers & PWA, 4.4 Intersection Observer, 4.5 Modern APIs, 4.6 BroadcastChannel/Storage Events. They sat under a mis-parsed "Table of Contents" section, and commit `ed0365e` deleted that section. The doc is now 2 intro paragraphs. `index.json` still lists the 6 headings, so search and the sidebar point at content that doesn't exist.

### K10. Broken links and migration leftovers
- 22 `[← Back to Overview](../../README-en.md|README.md)` paragraphs (last block of accessibility, architecture, css-layout, javascript, nextjs, nuxt, performance, react, state-management, state-management-react, typescript).
- 17 broken anchors:

  - Ids with a double hyphen, e.g. `./react.md#2021-context-vs-vue-provide--inject` (real id `2021-context-vs-vue-provide-inject`).

`index.json` is hand-maintained. Its rule is: `headings` = all level-2 and level-3 headings of the doc, and `summary` = doc `summary` cut to 219 chars plus "…". It is already stale for `web-apis`, and it will drift further with every rewrite unless it is regenerated.

22/29 soft and 26/27 situational items have no example story. Most give a list of "good structure" bullets instead of a worked STAR answer: Situation, Task, Action, Result.

### Q7. Overlapping questions with no clear scope
Several clusters cover the same ground with no scoping or cross-reference:

### X1. Technical accuracy must be re-checked while rewriting
Spot checks found errors, so the dense style is hiding mistakes:
- `js-var-let-const`: "`var` in a loop with `await` so every iteration fires the last id". Wrong. A sequential `await` doesn't cause this; the classic bug is `var` plus a callback *scheduled* inside the loop (`setTimeout`, `.then`, event handler).
- `vue3` 5.1.1 lists the patch flag `HYDRATE_EVENTS`. It was renamed `NEED_HYDRATION` in Vue 3.4.

Every rewritten claim about API behaviour must match current docs: Vue 3.5, Nuxt 3/4, React 19, Next 15, TypeScript 5.x. When something is version-specific, say which version.

## 2. Style guide and templates

### 2.1 Voice and depth (both KB and Q&A)

1. **Intuition before jargon.** Start each topic with a plain sentence a mid-level developer understands, then the mechanism, then the senior nuance.
2. **Define every term on first use in a topic or answer**, inline: "INP (Interaction to Next Paint: how long the page takes to visually respond after a click or key press)". Define an acronym again in each topic, because readers jump straight to anchors.
3. **One idea per sentence, one idea per bullet.** Bullets ≤ 220 chars. Paragraphs ≤ 450 chars (3–4 sentences). No `Decision. / Why. / Trade-off.` packed bullets.
4. **Complete sentences.** No arrow chains (`A → B → fails`) and no slash lists (`foo / bar / baz`) in prose. Arrows are fine inside tables and code comments.
5. **Senior level stays.** Every topic must still cover the trade-offs, at least one internal mechanism, and a real-world decision ("in a dashboard with X, I'd pick Y because…"). Simplifying the language must not drop the depth.
6. **Vue/Nuxt first, React/Next as a mapping.** Parker's strength is Vue. In React/Next docs, give the Vue equivalent in one sentence where it helps.
7. **Don't invent Parker's history.** For soft/situational stories, reuse details already in the current content (internal admin product, search race condition fixed with `AbortController`, Vue/Nuxt/TS, about 5 years). Where a story needs a specific number or name, use a bracketed placeholder like `[metric]` or `[team size]`, at most 2 per answer.
8. **Accuracy (X1).** If unsure about a behaviour, leave it out rather than guess. State versions for anything that changed recently.
9. en: "you" when explaining, "I" in model interview answers. vi: "bạn" when explaining, "tôi" in model interview answers.

### 2.2 KB leaf-topic template (each H3/H4 topic that has content)

Keep the existing `heading` block, including its `id`. Then use these blocks **in this order**. A "required" block must be present; an "optional" one is included only when it adds value.

| # | Block | Label / lead-in (en / vi) | Content | Target |
| --- | --- | --- | --- | --- |
| 1 | `paragraph` (required) | lead-in `**In short:**` / `**Tóm tắt:**` | What it is, in plain words: 1–2 sentences, no undefined term | ≤ 300 chars |
| 2 | `paragraph` (required) | lead-in `**Why it matters:**` / `**Vì sao quan trọng:**` | The problem it solves or the bug it prevents, in a real app | ≤ 450 chars |
| 3 | `paragraph` or `list` (`ol`) (required) | lead-in `**How it works:**` / `**Cách hoạt động:**` | The mechanism, step by step, defining terms inline. Optionally add a `callout` `tip` with an analogy | 2–6 steps |
| 4 | `code` (required for technical topics) | none | Minimal runnable example, 8–30 lines. Comments mark the key line and the expected output (`// logs: A, D, C, B`). Optionally a 2nd `code` block for the "fixed" version | 1–2 blocks |
| 5 | `paragraph` (required when there's code) | lead-in `**What happens here:**` / `**Điều gì xảy ra:**` | Walk through the example | ≤ 450 chars |
| 6 | `table` (optional) | none | Only when comparing ≥ 2 options. ≤ 5 rows × ≤ 4 columns, cells ≤ 120 chars, no claims that need nuance | |
| 7 | `senior-answer` (required) | `Senior perspective` / `Góc nhìn senior` | 3–5 bullets in markdown: trade-offs, internals, when NOT to use it, how to measure or verify. Each bullet is one idea | 600–1,100 chars |
| 8 | `callout` `warning` (required) | text starts `**Common pitfalls**` / `**Lỗi hay gặp**` | 3–4 bullets in markdown, each giving the symptom, the cause and the fix | ≤ 700 chars |
| 9 | `senior-answer` (required) | `What interviewers really ask` / `Nhà tuyển dụng thực sự hỏi gì` | The realistic question behind the textbook one (keep the good scenarios from the old `What they actually ask`, but in plain words) | ≤ 400 chars |
| 10 | `senior-answer` (required) | `How to answer in the interview` / `Trả lời khi phỏng vấn` | A spoken 45–60 s answer: definition, then mechanism, then one trade-off, then one real example. First person | 600–900 chars |
| 11 | `key-takeaways` (required) | none (the app adds the label) | 3–5 items that **summarise this topic**, no new information | each ≤ 160 chars |
| 12 | `senior-answer` (required) | `Likely follow-up questions` / `Câu hỏi nối tiếp thường gặp` | Markdown list of 3–4 items: `- **Question?** One- or two-sentence answer.` Replaces the old orphan list (K5) | ≤ 900 chars |
| 13 | `thematic-break` (required) | | | |

Length per topic (en, all text blocks): technical topics 4,500–7,500 chars; process/leadership/soft topics (`leadership`, `practical-questions`, `devops`, `monitoring`, parts of `system-design`) 3,000–5,000 chars. The vi length should land within 0.85–1.25× of the en length.

Rules:
- **Remove** the old labels `What they actually ask`, `Takeaway` and `Interview phrasing`, and the 4-bullet `Decision/Why/Trade-off/How to verify` list. Fold any useful content into blocks 3, 7, 8 and 9. `scripts/check-content.mjs` uses the new labels to tell migrated topics from legacy ones (section 5).
- Don't add new headings inside a topic (no H5/H6). Use bold lead-ins. Headings feed the in-page TOC and search.
- Group headings with no content (e.g. "1.1. Core Concepts") stay as they are. Translate their vi text only (see 2.5).
- Topics that are **comparison sheets** (e.g. `react` "Quick Vue → React cheat sheet", `nextjs` 21.10 caching cheat sheet) may skip blocks 3–5 and keep a larger table, but still need blocks 1, 7, 10 and 11.

**Doc-level blocks** (section `intro` of each doc):
- H1 + 2 paragraphs. Paragraph 1 says what the doc covers and who it's for, in plain language. Paragraph 2 says how to study it: which topics to read first and which ones interviewers ask most.
- `summary` (doc field): 1–2 plain sentences, ≤ 300 chars. The index uses the first 219 chars, so the first sentence must stand alone.
- Delete the trailing `[← Back to Overview](../../README…)` paragraph (K10).

### 2.3 Q&A answer template

Fields: never change `id` or `category`. You may append `tags` (lowercase kebab-case). `question` may be lightly clarified, but keep its meaning.

**Technical (`category: technical`)** — `answer` is markdown with these bold labels, in order, separated by blank lines:

```md
**Short answer:** 1–2 plain sentences that directly answer the question.

**Explanation:** 1–3 short paragraphs. Intuition first, then the mechanism. Define each term inline.

**Senior perspective:**
- 3–4 bullets: trade-offs, internals, when not to use it, how you'd verify it in production.

**Common pitfalls:**
- 2–3 bullets: symptom, then cause, then fix.

**How to say it (about 45 s):**
> One spoken paragraph in first person, 90–140 words.
```

- `example` (required): a code block with a lang tag (` ```ts `) and an expected-output comment, 8–30 lines, followed by 1–2 sentences explaining it. For conceptual questions with no natural code (e.g. `testing-pyramid`), use a small concrete scenario instead: a table, or a before/after.
- `followUps` (required): 2–3 plain-text questions, **no markdown** (no backticks, no `**`), each ≤ 120 chars.
- Length: `answer` 1,800–3,200 en chars; `example` 300–1,200.

**Soft (`category: soft`) and situational (`category: situational`)**:

```md
**What they are checking:** 1–2 sentences on the signal the interviewer wants (ownership, judgment, communication…).

**How to structure it:**
1. 3–5 steps (STAR for stories; "clarify, then options, then decision, then follow-through" for scenarios).

**Senior signals to include:**
- 2–4 bullets.

**Avoid:**
- 2–3 bullets.
```

- `example` (required): a **spoken model answer** of 600–1,200 chars, 60–90 s, first person, with Situation, Task, Action and Result visible. Situational system-design items (e.g. `design-autocomplete`, `design-news-feed`) use a walk-through instead: requirements, then components, then data flow, then the trade-offs you name.
- `followUps` (required): 2–3, plain text.
- Length: `answer` 1,000–2,200 en chars.
- vi labels: `**Trả lời ngắn:**`, `**Giải thích:**`, `**Góc nhìn senior:**`, `**Lỗi hay gặp:**`, `**Nói khi phỏng vấn (~45 giây):**`, `**Nhà tuyển dụng muốn thấy:**`, `**Cách trình bày:**`, `**Tín hiệu senior nên có:**`, `**Nên tránh:**`.

Q&A markdown rules:
- No `#` headings in Q&A (cards are small).
- **No links** in Q&A. `QuestionCard` has no KB link resolver, so a relative link would 404. Refer to KB topics in words instead ("see the Event Loop topic in the JavaScript doc").
- Overlap clusters (Q7): each item must state its own angle in its first sentence and must not repeat the sibling item's core example. The scope per item is listed in section 3.2.

### 2.4 Code example rules

- `lang` must be one of `ts`, `tsx`, `vue`, `js`, `css`, `html`, `json`, `bash`, `text`. Normalise the existing `txt` and `markdown` to `text`.
- Default to Vue 3 `<script setup lang="ts">` or plain TS. Use React `tsx` only in React/Next docs.
- 8–30 lines; must make sense if copied (imports may be omitted if obvious). Mark the key line with a comment. Show expected output for ordering or behaviour demos.
- Prefer "bug then fix" pairs (two `code` blocks, or one block with `// ❌` / `// ✅` comments).
- **en/vi code is identical except for comments.** Keep the same line count; translate comments only, never identifiers or strings that the code prints and the text refers to.

### 2.5 Vietnamese rules

1. Write natural Vietnamese prose for vi readers. Don't translate en word by word, and replace idioms with what they mean (see K7).
2. Keep standard English dev terms that Vietnamese FE devs use as-is: component, props, state, render, re-render, hook, composable, closure, event loop, microtask, hydration, bundle, cache, deploy, rollback, middleware, store. Format code identifiers in backticks.
3. Translate generic words. Never leave English grammar words or verbs in a vi sentence ("set", "freeze", "page", "measure", "decision", "warmup"). On first use per topic, give the Vietnamese term followed by the English one in parentheses.
4. Translate all labels and generic headings. Example: "1.1. Core Concepts" becomes "1.1. Khái niệm cốt lõi". **Keep the heading `id.vi` unchanged** (see 2.6).
5. **Structural parity:** the same blocks in the same order, the same number of list items, table rows and code lines, the same bold labels, and the same number of code spans per block (±2).
6. Glossary (use consistently):

| main thread | luồng chính (main thread) |

### 2.6 JSON field conventions (so the site keeps rendering)

- Every user-facing string is `{ "en": "...", "vi": "..." }`, both non-empty. Don't add new top-level fields to docs or questions. The app's types won't read them.
- Allowed block types: `heading`, `paragraph`, `list` (`style` ul/ol), `callout` (`kind` note/warning/tip/quote), `code` (`lang`, `code`), `table` (`headers`, `rows`, optional `align`), `senior-answer` (`label`, `text`), `key-takeaways` (`items`), `markdown`, `thematic-break`. Required fields are as in `schema/content.schema.json`.
- `senior-answer.label`: plain text, no markdown. `followUps`: plain text, no markdown.
- **Heading ids are permanent.** Never edit `heading.id.en` or `heading.id.vi`, even if you improve the heading text. Search, links and bookmarks depend on them. Exception: the H4 fragments removed in K8. Delete them only after `check-content` confirms no link targets them.
- In-KB links: same doc uses `[text](#<id>)`, other docs use `[text](./<slug>.md#<id>)`. The `<id>` must be the id **of the same locale**.
- Don't split `qna/questions.json` and don't reorder its items. The site shows items in file order.
- After touching any doc, run `node scripts/sync-kb-index.mjs` (created in B00) so `knowledge-base/index.json` matches.
- Preserve 2-space JSON indentation and the existing key order (`type` first). Write files with `JSON.stringify(data, null, 2) + "\n"`.
